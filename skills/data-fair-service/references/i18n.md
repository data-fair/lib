# Internationalisation of a service (fr + en)

Target: every screen, date and number of a service exists in French and English. English comes first in the code.
The UI mechanics are the same as in applications: the "Internationalisation" section of the `data-fair-app` skill
(per-component `<i18n>` blocks, `@intlify/unplugin-vue-i18n`, `n()` and named number formats) applies as is.
This file lists what is specific to services. Models to copy: portals, data-fair and metrics.

## UI

- **`createI18n` on the session**, after `await createSession(...)`:
  `createI18n({ legacy: false, locale: session.lang.value, fallbackLocale: 'en' })`. Never reassign the locale:
  a language switch reloads the page.
- **One `<i18n lang="yaml">` block per component**, `en` then `fr`, same keys in both (plurals included,
  `a | b | c`). No hardcoded French in templates, `aria-label`, `title`, chart labels or `uiNotif` messages.
- **Document language.** `index.html` keeps a static `<html lang="en">`, like the rest of the code: it only
  applies until the JS runs. `App.vue` replaces it with the session language:
  `watchEffect(() => { document.documentElement.lang = session.lang.value ?? 'fr' })`, or
  `useHead({ htmlAttrs: { lang: () => session.lang.value ?? 'fr' } })` when the UI uses unhead. The defect is a
  frozen `lang` (a screen reader reads French with an English voice, RGAA 8.3), not an English one: do not set
  `lang="fr"` in `index.html` because the session defaults to `fr`.
- **Dates**: `useLocaleDayjs()` with localized formats (`L`, `LL`, `lll`, `LT`, `LTS`, `fromNow`), never
  `'DD/MM/YYYY'`, `'D MMM YYYY à HH:mm'` or `new Date().toLocaleString()`.
- **Numbers and sizes**: always pass the session locale: `v.toLocaleString(locale.value)`,
  `formatBytes(v, locale.value)` (its default is `'fr'`). `toLocaleString()` without argument follows the browser,
  not the session.

## Schemas shown in a form

English base, French in `x-i18n-title.fr` / `x-i18n-description.fr`, rendered with `xI18n` and the session
locale. Never an `x-i18n-*` override with `en` alone: json-layout would show it to French users too. Details in
the `vjsf` skill.

## Server

- **Logs and error messages stay in English.** Translating API errors server side (`i18nHttpError` and the
  request language) is data-fair's choice only: ask the maintainer before adopting it in another service.
- **Notifications sent to events** carry `title` and `body` as `{ fr, en }`; events picks the language of each
  subscription. Keep every text in one table (`portals/api/src/utils/event-texts.ts`,
  `catalogs/shared/event-texts.ts`) with a unit test that checks the fr/en keys and parameters match.
- **Subscriptions.** The events subscribe embed sends the language of its interface. A service that subscribes
  server side sends `locale`, or forwards the user's cookie so events can take the session language.
- **Texts written into data or sent to remote platforms** (column titles, resources published on a CKAN or
  udata) stay in one language until the maintainer decides otherwise.

## Check before handing back

- A script comparing the fr and en keys of every `<i18n>` block, and the keys used by `t()` that no block declares.
- A grep for French outside the `<i18n>` blocks (accented letters, common words).
- `toLocaleString(`, `toLocaleDateString(`, `toLocaleTimeString(` and `formatBytes(` without a locale argument.
